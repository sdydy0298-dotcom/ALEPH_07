# T07 인증 구현 설명서

이 문서는 T07 요구사항의 인증 설명서 ①~⑥ 형식에 맞춰 작성했습니다. 실제 HTTP 상태와 캡처 파일명은 배포 후 `docs/T07_EVIDENCE_GUIDE.md` 순서로 확인해 최종 제출문에 옮깁니다.

## ① 무엇으로 붙였나

PlanDoSee는 **직접 구현한 이메일/비밀번호 인증 + 서버 저장형 불투명 세션(opaque session)** 방식을 사용합니다.

- 비밀번호 해시: `bcryptjs 3.0.2`, bcrypt cost 12
- DB 연결: `pg 8.16.3`
- 세션 값 생성: Node.js 내장 `crypto.randomBytes(32)`
- 세션 DB 저장: 원문 대신 SHA-256 해시
- 브라우저 전달: `HttpOnly; SameSite=Lax; Path=/; Max-Age=28800`, HTTPS에서는 `Secure`
- 세션 수명: 8시간

JWT 서명용 비밀키는 사용하지 않습니다. 로그인 성공 시 만든 무작위 세션 원문은 HttpOnly 쿠키에만 전달하고, 서버 DB에는 그 세션 값의 SHA-256 해시만 저장합니다.

## ② 왜 그걸 골랐나

검토한 대안은 **Supabase Auth**와 **JWT 기반 인증**입니다.

- Supabase Auth를 선택하지 않은 이유: 인증 서비스가 많은 동작을 대신 처리해 주기 때문에 이번 과제에서 요구하는 비밀번호 저장 방식, 로그인 실패, 세션 만료, 로그아웃 후 무효화, 비밀번호 변경 후 기존 세션 무효화를 내 소스와 DB에서 직접 설명하기가 상대적으로 어렵습니다.
- JWT를 선택하지 않은 이유: 브라우저 저장 위치와 토큰 폐기 전략을 추가로 설계해야 하고, 즉시 로그아웃/전체 세션 무효화를 위해 별도 폐기 목록 또는 세션 저장소가 다시 필요합니다.
- 서버 저장형 세션을 고른 이유: 세션의 발급·만료·삭제를 DB에서 직접 확인할 수 있고, 로그아웃과 비밀번호 변경 직후 기존 세션을 즉시 무효화할 수 있어 이번 검증 항목과 잘 맞습니다.

## ③ 어디를 어떻게 고쳤나

| 흐름 | 주요 소스 | 동작 |
| --- | --- | --- |
| 가입 | `api/auth.js`, `api/_lib/auth.js` | 이메일 정규화 → 비밀번호 검증 → bcrypt 해시 저장 → 세션 생성 |
| 로그인 | `api/auth.js`, `api/_lib/auth.js` | 같은 오류 문구 사용 → bcrypt 비교 → 세션 생성 → HttpOnly 쿠키 발급 |
| 로그아웃 | `api/auth.js`, `api/_lib/auth.js` | 현재 세션 DB 행 삭제 → 쿠키 만료 |
| 로그인 상태 확인 | `api/auth.js`, `api/_lib/auth.js` | 쿠키 원문을 SHA-256으로 해시 → DB 세션/만료 확인 |
| 계획/할 일/기록 조회 | `api/plans.js`, `api/tasks.js`, `api/executions.js`, `api/review.js` | `requireUser()`로 로그인 확인 후 `plans.user_id = session user_id`를 기준으로 소유권 제한 |
| 비밀번호 변경 | `api/auth.js` | 현재 비밀번호 재확인 → 새 bcrypt 해시 저장 → 기존 세션 전체 삭제 → 새 세션 1개 발급 |
| 계정 삭제 | `api/auth.js` | 비밀번호 재확인 후 `app_users` 삭제. FK `ON DELETE CASCADE`로 계획/할 일/기록도 함께 삭제 |
| T06 자료 이관 | `database/migrate_t06_owner.sql` | 기존 `plans.user_id IS NULL` 자료를 사용자가 만든 T07 계정에 1회 연결 |

데이터 격리의 기준은 클라이언트가 보낸 사용자 ID가 아니라 **서버 세션에서 확인한 사용자 ID**입니다. 요청 URL·헤더·본문에 임의의 다른 사용자 ID를 넣어도 권한 판단에는 사용하지 않습니다.

## ④ 안 열리는 것을 확인한 기록

아래 표의 `실제 결과`와 `증거 파일`은 **배포 후** 두 시험 계정 A/B로 채웁니다. 비밀번호와 세션 원문은 캡처에 포함하지 않습니다.

| 확인 | 성공 요청 | 거절 요청 | 기대 결과 | 실제 결과 / 증거 |
| --- | --- | --- | --- | --- |
| 로그인 전/후 동일 조회 | 로그인 후 `GET /api/plans` | 로그아웃 후 같은 `GET /api/plans` | `200` / `401` | 배포 후 기록 |
| 다른 계정 읽기 | A가 A의 `GET /api/tasks?planId=A_PLAN` | B가 같은 주소 요청 | `200` / `404` | 배포 후 기록 |
| 다른 계정 수정 | A가 A의 할 일을 `PATCH /api/tasks` | B가 A의 taskId로 같은 종류 요청 | `200` / `404` | 배포 후 기록 |
| 다른 계정 삭제 | A가 자신의 시험 자료 삭제 요청 | B가 A의 ID로 삭제 요청 | 성공 / `404` | 배포 후 기록 |
| 목록/소유자 변조 | A의 `GET /api/tasks` | B 로그인 상태에서 URL·헤더·본문에 A 식별자를 추가 | B의 자료만 반환 | 배포 후 기록 |

거절 전후에는 반대편 계정의 계획/할 일 개수가 변하지 않았는지도 함께 기록합니다. 세부 순서는 `docs/T07_EVIDENCE_GUIDE.md`를 따릅니다.

## ⑤ AI와 나

최종 제출문에는 아래 세 줄을 그대로 복사하기보다 실제 작업 내용을 확인한 뒤 필요한 표현만 다듬어 사용합니다.

- **AI에게 맡긴 일:** 인증 구조와 API 초안 작성, 요구사항 대조, 오류 점검, 테스트 절차와 UI 구현 보조를 맡겼습니다.
- **내가 직접 판단한 일:** PlanDoSee의 계획→할 일→결과 보기 흐름, 계획/할 일 화면의 정보 우선순위, 과제용 5일 조건을 메인 기능처럼 노출하지 않는 방향, 최종 디자인과 배포 방식을 직접 판단했습니다.
- **AI 제안을 따르지 않은 일:** 초기 시안의 5일 기록 강조, 우측 상세 패널, 복잡한 홈 카드 구성은 실제 사용성이 낮다고 판단해 사용하지 않고 여러 차례 다시 설계했습니다.

## ⑥ 아직 못 막은 것

현재 로그인 실패 보호는 **계정 단위 5회 실패 → 10분 잠금**입니다. IP/기기 단위의 별도 rate limit은 없습니다.

따라서 공격자가 특정 이메일을 알고 의도적으로 실패 로그인을 반복하면 그 계정을 일시적으로 잠그는 **가용성 저하(계정 잠금 유도)**가 가능합니다. 실제 상용 서비스라면 계정 단위 잠금만 사용하지 않고 IP/기기/위험도 기반 제한, CAPTCHA 또는 별도 인증 보호를 함께 적용해야 합니다.

또한 이메일 인증과 비밀번호 재설정 기능은 이번 범위에 포함하지 않았습니다. 따라서 비밀번호를 잊은 사용자는 운영자 도움 없이 계정을 복구할 수 없습니다.
